Architecture overview

One durable event, two independent destinations

The payment and its outbox event are committed together. Kafka serves internal applications, while webhooks cross the system boundary to merchant servers.

Payment API→SQL + Outbox→Kafka
Kafka→Listener→Audit DB
Outbox→Webhooks→Merchant

Read one event from left to right

What changes after a payment is created?

  1. 1
    SQL transaction

    The payment and outbox event become durable together.

  2. 2
    Kafka publication

    Published increases and Kafka assigns a partition and offset.

  3. 3
    Internal consumption

    Consumed increases and lag returns to zero after the listener stores it.

  4. 4
    External notification

    The webhook dashboard records the merchant server's HTTP response.

Compare the responsibilities

Kafka and webhooks solve different boundaries

Kafka

Internal, durable and pull-based communication.

With Kafka

Independent services consume the same event through their own consumer groups.

Without Kafka

The payment request must call every internal task directly.

Webhooks

External, signed and push-based communication.

With webhooks

The merchant receives automatic notifications and FinPay records retries.

Without webhooks

The merchant repeatedly polls the payment API to discover changes.

Independent listener

A consumer that can stop without stopping payments.

Listener running

Offsets advance and the audit projection stays current.

Listener stopped

Kafka retains records and lag grows until the listener returns.

Interview-ready vocabulary

Core concepts

Transactional outbox

Keeps the payment and its future notification consistent.

Topic

The named Kafka stream where related events are retained.

Partition

An ordered portion of a topic that enables parallel processing.

Offset

The record's sequential position inside one partition.

Consumer group

Tracks progress and distributes partitions between consumer instances.

At-least-once

Protects against lost events, so consumers deduplicate by event ID.

Dead Letter Topic

Isolates a poison message after retries so later records can keep moving.

Try it yourself

Three controlled experiments

A

Stop the listener

docker compose stop kafka-listener

Create a payment. Published grows, Consumed pauses and Consumer lag increases.

docker compose start kafka-listener

The listener catches up and lag returns to zero.

B

Stop the webhook receiver

Create or update a payment while the merchant endpoint is unavailable.

Kafka can still publish and consume, while the webhook dashboard records a failed HTTP delivery and retry.

C

Send an invalid Kafka record

The listener retries it three times, moves it to the Dead Letter Topic and then continues with the next valid record.

Dead letters increases while normal Consumer lag can return to zero, proving the poison message no longer blocks its partition.
