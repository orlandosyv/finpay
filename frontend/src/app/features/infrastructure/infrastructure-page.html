The idea in one minute

One durable event, two delivery channels

The API first commits the payment and its outbox event in one SQL transaction. Background workers later deliver that same event through Kafka and webhooks. A temporary outage does not erase the event.

Why these tools exist

With the tool vs. without it

Kafka

With Kafka

Multiple internal consumers can process the same durable event independently.

Without Kafka

New internal tasks are coupled directly to the payment request or database.

Webhooks

With webhooks

The merchant receives signed notifications automatically, including retries.

Without webhooks

The merchant must poll FinPay repeatedly to discover payment changes.

Interview-ready concepts

What each pattern solves

Transactional outbox

Prevents a payment from being committed without first leaving a durable event to publish.

Kafka

Decouples internal consumers so analytics, auditing, or fraud detection can evolve independently.

Webhooks

Push signed HTTP notifications across the system boundary to merchant-owned servers.

At-least-once

Prioritizes not losing events; consumers must deduplicate with the event ID.

Step 2 is active

“Connected” proves only that the broker is reachable. A PUBLISHED row with a partition and offset proves that a concrete payment event was accepted by Kafka. Stop Kafka, create a payment, and restart it to see the durable outbox and retry mechanism in action.
